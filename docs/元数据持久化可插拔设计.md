# QOF 元数据持久化可插拔设计

| 项 | 内容 |
|---|---|
| 文档版本 | 1.3 |
| 适用代码基线 | 17.2.x；现状模块仍为 `qof-persistence-mybatis`，**目标更名为** `qof-persistence-mysql` |
| 目标读者 | 组件维护者、业务接入方架构师 |
| 状态 | 方案稿（待选型后落地） |

---

## 1. 背景与目标

### 1.1 背景

对象存储侧（local / cos / oss / s3）已按 Provider 模式可裁剪接入；文件**元数据**（现 `sys_files`）仍绑死 MyBatis-Plus：

- `FileMetadataRepository` 已在 `qof-spi` 声明，但**未接入运行时**
- 实际上传落库走 `QofExtService` → `FilesService` → `SysFiles`
- `FilesService extends IService<SysFiles>`，接口泄漏 MyBatis
- Web 层直接依赖 `FilesService`，换 Mongo / ES / Redis 必然断裂

### 1.2 目标

1. **元数据存储与对象存储解耦**：fileId 语义由元数据仓储提供，与字节存在哪无关  
2. **可切换后端**：MySQL、SQLite、MongoDB、Elasticsearch、Redis 等均可作为实现  
3. **业务按需引依赖**：只引需要的 starter，不背无关驱动  
4. **能力诚实**：不是所有后端都能等价支持「模糊分页列表」；SPI 分层表达能力  
5. **元数据持久化强制**：不允许「只要对象存储、不落元数据」。上传/下载/删除主路径必须以可持久化的 `FileMetadataRepository` 为准；未装配实现时**启动失败**  

### 1.3 硬约束（接入契约）

| 约束 | 说明 |
|---|---|
| 禁止 Noop 业务模式 | 不提供、不文档化 `metadata.type=noop` 作为合法业务配置 |
| 依赖成对出现 | 业务至少：`qof-spring-boot-starter`（或等价）**+** 某一个 `starter-persistence-*`（或自实现 Repository Bean） |
| 启动失败快速 | classpath / 容器中不存在 `FileMetadataRepository` Bean → 应用启动报错，提示需引入 persistence starter |
| fileId 一等公民 | 上传必须落元数据；下载/删除必须能按 fileId 查到路径与存储模式 |

### 1.4 非目标（本期可不做）

- 不一次实现全部后端（可先 MySQL + 一个样例后端）  
- 不强制统一宿主鉴权 / 统一 `Result` 模型  
- 不做跨后端自动数据迁移工具（迁移脚本由运维/业务自行处理）  
- 不支持「纯对象存储、调用方自持 key」的产品形态（与硬约束冲突）

## 2. 现状诊断

```text
当前实际链路（问题态）

  QofClient.upload/download/delete
           │
           ▼
     QofExtService  （钩子 + 落库混在一起）
           │
           ▼
      FilesService  （IService<SysFiles>，MyBatis 专用）
           │
           ▼
        SysFiles / MySQL

  FileMetadataRepository ──（定义存在，运行时未使用）──► ✗
```

| 模块 | 现状角色 | 问题 |
|---|---|---|
| `qof-spi` | 声明了空转的 `FileMetadataRepository` | 类型为 `Object`，无强契约 |
| `qof-core` | `NoopQofExtService`；Client 只认 `QofExtService` | 未依赖仓储 SPI |
| `qof-persistence-mybatis`（现状）→ 目标 `qof-persistence-mysql` | `FilesService` + `AbstractQofServiceImpl` | 实现细节外溢；模块名应表达存储后端 MySQL，而非 ORM |
| `starter-persistence` | 仅聚合现 mybatis 实现 | 命名像「通用持久化」，实际是 MySQL 专用 |

## 3. 统一契约（三条路径共用）

无论选哪条路径，对外契约建议统一如下（路径 1 可先做子集）。

### 3.0 命名约定（重要）

| 层级 | 命名规则 | 示例 |
|---|---|---|
| 模块 / starter / `metadata.type` | 按**存储后端**命名 | `mysql`、`sqlite`、`mongodb`、`redis`、`es` |
| 实现技术 | 留在模块内部，**不进入对外 artifactId** | MySQL/SQLite 都可能用 JDBC；MySQL 模块内部还可用 MyBatis-Plus，但都不叫 `*-jdbc` / `*-mybatis` |

> **不要**把 `jdbc` 当成与 `mysql` 平级的 type：JDBC 是驱动/访问层，MySQL、SQLite 都走 JDBC。对外只区分存储后端。

因此：`qof-persistence-mysql` / `qof-spring-boot-starter-persistence-mysql` / `qof.metadata.type=mysql`。  
现状仓库中的 `qof-persistence-mybatis` 在落地本设计时应**重命名**为 `qof-persistence-mysql`（可保留旧坐标一版本作别名）。

### 3.1 中立模型（建议放 `qof-spi`）

```java
/** 文件元数据中立模型：与表结构 / 文档结构无关 */
public class FileMetadata {
    private Long fileId;
    private String fileName;
    private String filePath;
    private String fileType;
    private String fileLabel;
    private Long fileSize;
    private String fileStorageMode;
    private String fileStorageStation;
    private Integer publicAccess;
    private Long createId;
    private LocalDateTime createTime;
    private LocalDateTime updateTime;
    // 不含 MyBatis @TableLogic 等实现注解
}
```

> 现有 `QofFileInfoBo` 可与之互转；`SysFiles` 降为 mysql 模块**内部实体**。

### 3.2 必选 SPI：按 ID 读写（所有后端均需实现）

```java
public interface FileMetadataRepository {

    /** 后端类型标识：mysql / sqlite / mongodb / es / redis / custom */
    String type();

    Optional<FileMetadata> findById(Long fileId);

    /** 新增；返回 fileId（通常与入参一致，雪花已在 Client 生成） */
    Long save(FileMetadata metadata);

    /** 全量或按约定字段更新 */
    void update(FileMetadata metadata);

    /** 逻辑删除或物理删除（由实现决定，需在文档声明） */
    boolean deleteById(Long fileId);
}
```

### 3.3 可选 SPI：查询能力（关系库 / Mongo / ES 实现；Redis 可不提供）

```java
public interface FileMetadataQuery {

    PageResult<FileMetadata> page(FileMetadataQueryCriteria criteria);
}

public class FileMetadataQueryCriteria {
    private long pageNum = 1;
    private long pageSize = 10;
    private String fileName;            // 模糊，可选
    private String fileStorageMode;     // 可选
    private String fileStorageStation;  // 可选
}
```

### 3.4 能力矩阵

| 能力 | MySQL | SQLite | MongoDB | Elasticsearch | Redis |
|---|---|---|---|---|---|
| `Repository` 按 ID CRUD | ✅ | ✅ | ✅ | ✅ | ✅ |
| `Query` 模糊 + 分页 | ✅ | ✅ | ✅ | ✅ 强 | ❌ 不实现 |
| 强一致事务 | ✅ | ✅ | 有限 | ❌ | ❌ |
| 适合场景 | 默认业务库 | 嵌入式 / 单机 | 文档型扩展字段 | 检索 / 海量列表 | 缓存或极简 ID 索引 |

配置建议：

```yaml
qof:
  metadata:
    type: mysql          # mysql | sqlite | mongodb | es | redis | custom
    # 禁止同时装配多个「写」实现；以 type 为准做 ConditionalOnProperty
    # 禁止 type=noop；未装配任何 FileMetadataRepository 时启动失败
```

### 3.5 与对象存储、生命周期的关系

```text
业务 / Web
    │
    ├─ QofClientFactory → QofClient     （字节：local/cos/oss/s3）
    │
    └─ FileMetadataRepository[/Query] （元数据：必选，可插拔后端）

AbstractQofClient
    ├─ before/after* → FileLifecycleListener（可组合）
    └─ 默认落库 Listener / Ext 适配器 → 必须调用 FileMetadataRepository
         （无 Repository Bean = 启动失败，运行期不再走 Noop）
```

## 4. 方案一：最小改造（推荐首期）

### 4.1 定位

**打通并强化 `FileMetadataRepository`，MySQL 作为第一个官方后端（实现层可用 MyBatis-Plus）**；保留 `QofExtService` / `FilesService` 作兼容桥，业务可逐步迁移。

适合：尽快具备「可换后端」骨架，又不想一次打碎现有接入方。

### 4.2 模块调整

```text
qof-spi
  ├─ FileMetadata（新增中立模型）
  ├─ FileMetadataRepository（改为强类型）
  └─ （暂不强制 FileMetadataQuery）

qof-core
  ├─ MetadataBackedQofExtService   # 委托 Repository 做 afterUpload / getById / beforeDelete
  ├─ 启动校验：缺少 FileMetadataRepository → Fail Fast
  └─ 仍暴露 QofExtService（内部默认用 Repository；删除面向业务的 Noop 落库路径）

qof-persistence-mysql
  ├─ SysFiles（内部实体；实现可用 MyBatis-Plus）
  ├─ MysqlFileMetadataRepository implements FileMetadataRepository
  ├─ FilesService（@Deprecated，委托 Repository 或并行保留）
  └─ 自动配置：注册 Repository Bean；条件覆盖 Ext

qof-spring-boot-starter-persistence-mysql
  └─ 聚合 qof-persistence-mysql

兼容别名（Deprecated）：
  qof-spring-boot-starter-persistence
  qof-persistence-mybatis / starter-persistence-mybatis（历史名）
```

### 4.3 实现步骤

1. **SPI 强类型化**  
   - `Optional<Object>` → `Optional<FileMetadata>`  
   - `insert(Object)` → `save(FileMetadata)`  

2. **core 强制仓储**  
   - **不**再默认注册业务可用的 `NoopFileMetadataRepository`  
   - `MetadataBackedQofExtService`：  
     - `afterUpload` → **始终** `repository.save(...)`  
     - `getFileInfoByFileId` → `repository.findById`（不存在则业务异常）  
     - `beforeDelete` → `repository.deleteById`  
   - `@ConditionalOnMissingBean(FileMetadataRepository.class)` 时注册启动失败分析器 / `ApplicationContextInitializer`，错误信息明确要求引入 persistence starter 或自实现 Bean  

3. **mysql 实现（内部可用 MyBatis-Plus）**  
   - `SysFiles ↔ FileMetadata` 转换器  
   - `@Bean FileMetadataRepository` + `@ConditionalOnProperty(qof.metadata.type=mysql)`（缺省可默认为 mysql，当且仅当 mysql starter 在 classpath）  
   - 现有 `AbstractQofServiceImpl` 改为调用 Repository，或直接由 core 的 Ext 取代  

4. **兼容**  
   - `FilesService` 保留 1～2 个小版本：`@Deprecated`，内部转调 Repository  
   - Web `FileController` 暂可继续注入 `FilesService`，或改为注入 Repository  
   - 废弃 `persistent-enable=false`「上传可不入库」语义；旧配置若关闭持久化 → 启动警告并视为非法，或直接失败  

5. **验证**  
   - 引入 mysql starter 后，上传返回 fileId，下载按 fileId 可查路径  
   - **仅**引入 `qof-spring-boot-starter`、不引 persistence、也不自实现 Repository → **启动失败**  

### 4.4 配置示例

```yaml
qof:
  metadata:
    type: mysql
  # 过渡期：旧键 persistent-enable 仅允许 true；false 视为非法配置
  local:
    enable: true
```

## 5. 方案二：完整可插拔

### 5.1 定位

在方案一骨架上：

- 拆出 **`FileMetadataQuery`**
- **按后端拆分 persistence 模块与 starter**
- 官方至少再提供 **一个非 MySQL 样例实现**（建议 SQLite 或 MongoDB）

适合：明确要「业务换一个依赖就能换元数据后端」。

### 5.2 目标模块结构

```text
qof-spi
  ├─ FileMetadata
  ├─ FileMetadataRepository          # 必选
  ├─ FileMetadataQuery               # 可选能力
  └─ FileMetadataQueryCriteria / PageResult

qof-core
  ├─ MetadataBackedQofExtService
  ├─ 启动校验：缺少 FileMetadataRepository → Fail Fast（无 Noop 业务实现）
  └─ （可选）Query 缺失时的友好异常 / 功能降级提示

qof-persistence-mysql                # MySQL（内部可用 JDBC + MyBatis-Plus）
qof-persistence-sqlite               # SQLite（内部可用 JDBC Template 等，不是「通用 jdbc 模块」）
qof-persistence-mongodb
qof-persistence-elasticsearch
qof-persistence-redis

qof-spring-boot-starter-persistence-mysql
qof-spring-boot-starter-persistence-sqlite
qof-spring-boot-starter-persistence-mongodb
qof-spring-boot-starter-persistence-es
qof-spring-boot-starter-persistence-redis

# 兼容：旧坐标 qof-spring-boot-starter-persistence → 等同 mysql（Deprecated）
```

### 5.3 实现要点

#### 5.3.1 自动配置互斥

```java
@AutoConfiguration
@ConditionalOnProperty(prefix = "qof.metadata", name = "type", havingValue = "mysql")
@ConditionalOnClass(name = "com.baomidou.mybatisplus.extension.service.impl.ServiceImpl")
public class MysqlMetadataAutoConfiguration {
    @Bean
    @ConditionalOnMissingBean(FileMetadataRepository.class)
    FileMetadataRepository mysqlFileMetadataRepository(...) { ... }

    @Bean
    @ConditionalOnMissingBean(FileMetadataQuery.class)
    FileMetadataQuery mysqlFileMetadataQuery(...) { ... }
}
```

同理：`type=sqlite` / `mongodb` / `es` / `redis`。

启动校验（建议）：

- **缺少** `FileMetadataRepository` Bean → **启动失败**（硬约束）  
- 若 classpath 上出现多个 persistence 实现且未配置 `qof.metadata.type` → **失败快速**并打印可选 type 列表  
- Redis 未实现 Query 时：Web 列表接口检测到无 `FileMetadataQuery` Bean → 返回 501 或文档约定关闭  

> 原则：**对象存储 starter** + **元数据 starter（按 type 必选其一）** + 可选 **web**。  
> 不要同时引入两个 metadata starter；也不允许只引对象存储、不引元数据。

#### 5.3.2 Web 层改造

```text
FileController
  ├─ 上传/下载/删除：QofClient + FileMetadataRepository（鉴权可读 metadata）
  └─ 分页列表：Optional<FileMetadataQuery> 或必需注入（无 Bean 则禁用接口）
```

禁止再依赖 `IService<SysFiles>` / MyBatis `Page`。

#### 5.3.3 各后端实现草图

| 后端 | 存储结构 | Repository | Query |
|---|---|---|---|
| MySQL | 表 `sys_files` | JDBC + MyBatis（实现细节） | `pageFiles` 迁入 |
| SQLite | 同构表或简化 DDL | JDBC Template 等（实现细节） | 同左 |
| MongoDB | collection `sys_files` | `MongoTemplate` / Repository | Criteria 分页 |
| ES | index `qof_file_metadata` | Index API | Search + from/size |
| Redis | `qof:file:{id}` Hash/JSON | `StringRedisTemplate` | **不实现** Query |

#### 5.3.4 落地顺序建议

1. 完成方案一  
2. 抽出 `FileMetadataQuery`，改造 Web 列表  
3. 拆 `starter-persistence-mysql`，旧 starter 别名兼容  
4. 实现 **SQLite 或 MongoDB** 之一作为样例  
5. 视需求再补 ES / Redis

#### 场景 F：兼容旧坐标（过渡期）

```xml
<!-- 等同 persistence-mysql，后续版本标记 Deprecated -->
<dependency>
  <groupId>io.github.codeyunze</groupId>
  <artifactId>qof-spring-boot-starter-persistence</artifactId>
  <version>${qof.version}</version>
</dependency>
```

## 6. 方案三：激进清理

### 6.1 定位

**对外只保留 SPI 中立模型 + Repository/Query**；删除或完全内化：

- `FilesService`（不再作为 Public API）  
- `SysFiles` 对外可见性  
- 以继承 `AbstractQofServiceImpl` / `@Primary` 整类覆盖作为「落库扩展」的文档路径  
- Web / examples 全部改为 SPI  

适合：大版本（如 18.0.0）破坏性升级，追求长期干净边界。

### 6.2 实现要点

1. **Public API 清单收敛**（建议写入 README / japicmp）  
   - 稳定：`QofClient`、`QofClientFactory`、`FileMetadata`、`FileMetadataRepository`、`FileMetadataQuery`、`FileLifecycleListener`、`ObjectStorageProvider`  
   - 移除对外：`FilesService`、`SysFiles`、`SysFilesMetaBo`（或迁到 `...internal` / 实现模块且不导出）  

2. **`QofExtService`**  
   - 标记 `@Deprecated(forRemoval = true)`  
   - 新代码只注册 `FileLifecycleListener`  
   - core 内置「MetadataPersistenceListener」调用 Repository  

3. **持久化模块**  
   - 仅实现 SPI；不暴露 MyBatis Mapper 给业务  
   - 业务若需原生 SQL/聚合，自行建表或绕过组件（文档声明）  

4. **升级指南**  
   - 提供 `FilesService` → `FileMetadataRepository` 对照表  
   - `SysFiles` 字段 → `FileMetadata` 字段映射  
   - 一版本双坐标过渡后删除旧 starter 别名  

5. **版本策略**  
   - 建议作为 **Major** 发布；方案一/二可在 17.x 完成，方案三进 18.x  

### 6.3 与方案二的差异

| 项 | 方案二 | 方案三 |
|---|---|---|
| 旧 API | Deprecated 保留 | 删除或实现模块私有 |
| 扩展方式 | Ext + Listener 并存 | 仅 Listener + Repository |
| 业务侵入 | 小 | 需改编译依赖与代码 |
| 模块裁剪 | 相同（按后端 starter） | 相同 |

### 6.4 业务模块实际引用的 QOF 依赖

依赖坐标与**方案二相同**（仍按存储 + 元数据后端组合）；差别在**业务代码只允许依赖 SPI/核心门面**。

#### 推荐依赖组合（与方案二场景 A 相同）

```xml
<dependency>
  <groupId>io.github.codeyunze</groupId>
  <artifactId>qof-spring-boot-starter</artifactId>
  <version>${qof.version}</version>
</dependency>
<dependency>
  <groupId>io.github.codeyunze</groupId>
  <artifactId>qof-spring-boot-starter-persistence-mysql</artifactId>
  <version>${qof.version}</version>
</dependency>
```

#### 业务代码约束（方案三强制）

```java
// ✅ 允许
@Resource QofClientFactory factory;
@Resource FileMetadataRepository metadataRepository;
@Resource FileMetadataQuery metadataQuery; // 若该后端提供

// ❌ 禁止（坐标上也不再传递）
// FilesService / SysFiles / AbstractQofServiceImpl
```

若业务需要「自定义元数据后端」（仍必须真实持久化，禁止 Noop）：

```xml
<!-- starter + 自实现 FileMetadataRepository；不可省略元数据落库 -->
<dependency>
  <groupId>io.github.codeyunze</groupId>
  <artifactId>qof-spring-boot-starter</artifactId>
  <version>${qof.version}</version>
</dependency>
<!-- 一般经 starter 已传递 qof-spi；若极致裁剪可显式： -->
<dependency>
  <groupId>io.github.codeyunze</groupId>
  <artifactId>qof-spi</artifactId>
  <version>${qof.version}</version>
</dependency>
```

```java
@Bean
@ConditionalOnMissingBean(FileMetadataRepository.class)
FileMetadataRepository myRepo() {
    return new MyCompanyMetadataRepository(); // 必须写入真实存储介质
}
```

```yaml
qof:
  metadata:
    type: custom
```

## 7. 三条路径对比与选型建议

| 维度 | 方案一 最小改造 | 方案二 完整可插拔 | 方案三 激进清理 |
|---|---|---|---|
| 工期 | 短 | 中 | 长（含破坏性迁移） |
| 可换后端 | 骨架具备，官方仍以 MySQL 为主 | 官方多 starter | 同方案二 + API 更干净 |
| 兼容旧业务 | 最好 | 良好（Deprecated） | 差（Major） |
| Web 列表 | 可暂留 FilesService | 必须走 Query SPI | 必须走 Query SPI |
| 推荐版本 | 17.3.x | 17.4.x～17.5.x | 18.0.0 |
| 业务依赖形态 | `starter` + `starter-persistence-mysql`（强制成对） | `starter` + `starter-persistence-*`（强制成对） | 同方案二，代码只认 SPI |

**建议节奏：**

```text
17.3  方案一落地（强类型 Repository + MySQL 实现接入 Client；缺 Repository 启动失败）
  │
17.4  方案二：Query SPI + starter 拆分 + 一个样例后端（sqlite/mongo）
  │
18.0  方案三：删除对外 FilesService / 旧 Ext 落库路径
```

## 8. 业务依赖速查（汇总）
